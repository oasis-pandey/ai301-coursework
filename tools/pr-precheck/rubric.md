# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| plan_fidelity | The plan-context scope, named files, promised behaviors, and deviation notes read side by side with every changed file and hunk in the candidate diff; the description's scope and completion claims read against both. | Pass when every substantive diff change is required by the plan or explicitly re-tied to it by a deviation that says what changed and why, and every still-promised plan outcome appears in the diff. An honestly documented deferral or narrower outcome passes when both the plan's deviation record and description disclose it. Fail for extra behavior, options, refactors, or files with no plan/deviation basis; silently missing promised work; or a description claiming work the diff does not contain. | required |
| test_evidence | The candidate test-evidence block read against the reproduction trigger, controls, and expected outcome in the plan context, each behavior actually delivered, and the description's testing claims. | Pass when the primary reported failure is shown before the change and with an observable contrasting result after it, or a focused regression test demonstrates the same contrast through the changed path. For secondary delivered behavior and non-deferred test-plan cases, a specifically named observed outcome or focused test result is sufficient; a second full transcript is not required. The evidence must expose a falsifiable output, state, exit result, or assertion and may honestly report failures. Fail for “tested” or “passes” without the primary decisive observable, a control or unchanged path substituted for the failing path, subjective duration/manual claims, or silence about a promised case. | required |
| repo_checks | The test-evidence block's commands and outcomes read against the repository checks, suites, and testing requirements named in repo facts, the PR template, contribution docs, or the live Path Review template. | Pass when every applicable repository-requested check is named with its actual outcome, including an expected no-tests result or an honestly reported failure; a check may be inapplicable only when the package gives a concrete repository-based reason. Fail when a required check was not run, its result is hidden, or a checked box/description claim is unsupported. | required |
| diff_reviewable | The entire unified diff and commit list, including context around the intended fix, read against the plan's bounded purpose. | Pass when the intended change is directly reviewable and no unrelated hunk or development debris rides along. Fail for debug prints, commented-out attempts or code, dead probes/helpers, unexplained TODOs, generated artifacts, bulk formatting/reindent/import churn, or drive-by edits that bury or enlarge the planned change. Commit wording alone never fails, but it may direct attention to debris that must be verified in the diff. | required |
| standards_compliance | The title and description read against every applicable template ask, contribution rule, explicit thread direction, and AI-use policy in repo facts or the live repository; required companion artifacts are verified in the diff. | Pass when the package substantively satisfies each stated ask: issue linkage, required sections/checklists, release-note or test requirements when applicable, maintainer direction, and an own-words AI-use disclosure whenever policy requires it. `N/A` passes only with a truthful reason. Fail when required content is omitted, boilerplate is left in place, a box is falsely checked, a required artifact is absent, or an applicable disclosure is missing. | required |
| reviewer_clarity | The candidate title and description read against the issue, plan, diff, and test evidence. | Pass when a reviewer can identify the problem, bounded delivered change, notable deviation or shortfall, and evidenced validation without a misleading promise. Minor terseness or style preferences do not fail this check. | preferred |

## Verdict rule

Return `accept` only when every required check passes. Return `reject` when any required check is `fail` or `unclear`; absent or unverifiable evidence cannot establish readiness. Preferred checks provide feedback only and never change the verdict, whether they fail or are unclear. Apply all rows independently: strength on one check cannot compensate for failure on another.
